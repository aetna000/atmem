Walkthrough

Investigating a flight, step by step

# 1. find recent runs
atmem blackbox runs --limit 50
# 2. read one run as a story
atmem blackbox story RUN_ID
# 3. prove the chain is intact
atmem blackbox verify RUN_ID
# 4. hand evidence to a reviewer
atmem blackbox export RUN_ID --format json
# 5. acknowledge a finding
atmem blackbox ack RUN_ID ATTENTION_CODE

Dashboard flight nodes

Green: no active finding

Amber: needs review

Red: failed run or incomplete evidence

Acknowledging a finding never deletes or rewrites evidence.

Let me walk you through how an investigation looks in practice. Say someone reports that the agent did something odd yesterday. Step one, find the run: “atmem blackbox runs” lists recent flights. Step two, “atmem blackbox story” with the run ID tells that run as a readable story: what came in, what memory was considered and injected, which tools were called, and how the turn ended. Step three, “atmem blackbox verify” proves the hash chain for that run is intact, so you know you’re looking at what was recorded and not something edited later. Step four, if a security or compliance reviewer needs the evidence, “atmem blackbox export” writes it as JSON or text. And step five, once you’ve dealt with a finding, “atmem blackbox ack” with its attention code acknowledges it. The dashboard shows the same thing visually. It opens with a concise action timeline. A flight node is green when no active finding remains, amber when it needs review, and red when the run failed or its evidence is incomplete. Select a node and you see the request and reply where a protected local reader can supply them, the memory used, tools and websites, model and provider, tokens, latency, risks, any blocking reason, outcome evidence and hashes. Most importantly, acknowledging a finding never deletes or rewrites evidence. The record stays.
