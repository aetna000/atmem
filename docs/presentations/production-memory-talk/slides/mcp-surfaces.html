MCP surfaces

Two MCP surfaces, two trust levels

For agents

Host control MCP

atmem control mcp

  • capture memory candidates
  • prepare context before a model call
  • confirm exact context exposure
  • record flight events
  • adapter sync and status

Cannot approve memory, acknowledge findings or activate AtMem.

For trusted operators

Operator MCP

atmem control operator-mcp

  • approve or reject memory
  • acknowledge findings
  • configure agent scopes
  • export evidence
  • activate, or return to shadow

Never expose it to an agent or an untrusted network.

Dashboard: loopback only · local account · HttpOnly session · origin and CSRF checks on every change

A key design decision in AtMem is that there isn’t one MCP server, there are two, with very different trust levels. This is the same idea as putting a gateway in front of your tools: the agent should never hold the keys to its own governance. On the left is the host control MCP, started with “atmem control mcp”. This is what agents talk to. It’s deliberately non-administrative. It can capture memory candidates, prepare context before a model call, confirm the exact context exposure, record flight events, and report adapter sync and status. That’s all. An agent can’t approve its own memories, acknowledge its own findings or switch AtMem into active mode. On the right is the operator MCP, started with “atmem control operator-mcp”. That one can approve or reject memory, acknowledge findings, configure agent scopes, export evidence, and activate AtMem or return it to shadow. It’s meant for a trusted local operator client, a human, and you should never expose it to an agent or an untrusted network. The dashboard follows the same principle: it binds only to loopback, requires a local AtMem account, uses HttpOnly sessions, and checks origin and CSRF on every mutation. Don’t put it behind a public reverse proxy.
