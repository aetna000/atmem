## Literal nomination contract

- Extract bounded identifier-like keys from inline code and explicit CLI flags,
  including assignment forms. Do not expand all prose words into literals.
- Inspect only already-verified in-memory source; parse as data, never execute,
  import, fetch a URL or access another scope/file. Bound keys and ambiguity.
- Recognize a module-level literal-key dictionary pointing directly to a unique
  same-module function definition. Reject unresolved, imported, multiply
  defined or explicitly rebound callable names. Do not resolve dynamic calls,
  arbitrary attributes, computed keys or runtime mutation/reachability.
- Recognize keys in immediate class-level dictionary or tuple/list declarations;
  nominate only the existing class owner, not an invented configuration object.
  Nested method strings and docstrings do not establish class ownership.
- Return only targets already represented by correctly bound CodeSymbol
  candidates. No module/file fact may acquire executable status. No new graph
  edge, authority record, canonical memory text or runtime guarantee is created.
- If a key maps to more than eight eligible targets, withhold that key's
  promotion rather than guessing. This is a bounded ranking policy, not a
  calibrated probability or proof that fewer targets are semantically correct.
- Explicit named references retain priority over literal hints. Direct callable
  bindings rank ahead of owner-only declarations. Existing lexical/graph
  nomination breaks bounded ties; budgets and truthful omission labels remain.

## URL conflict rule

When a current source file contains an explicitly referenced eligible symbol,
do not give an unverified URL-line nomination for a different symbol in that
same file precedence over it. Matching named/line targets retain their existing
priority. URL-only queries retain bounded line nomination. Both sources remain
eligible context; do not claim the URL's historical revision is current.
