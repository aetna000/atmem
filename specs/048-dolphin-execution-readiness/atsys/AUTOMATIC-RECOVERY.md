## What the supervisor can repair

`allowRepair:true`, supervised recovery, maximum 2 retries, maximum 3 supervisor
calls. Repairs may change the listed harness/export/recovery modules and focused
implementation tests/Spec Kit prose. The parent owns a separate immutable source
allowlist and verifies scientific identity, qualification artifacts, cumulative
budget rows and inherited result bytes independently of repairable verifiers.

The trusted parent, independent validators, task policy, private contract,
scientific descriptor, source/evidence bundles, product, upstream fixtures,
model/routes, memory, grading rules, saved results and budget cap are outside
coding repair scope. Their pins cannot be refreshed by the repair worker.

A command worker performs private/MEM operations; the coding repair worker retains
workspace scope. `resumeArgv` invokes the parent, which runs acceptance, freezes a
new harness revision, runs actual zero-model-call app/profile/crash qualification,
imports settled evidence and resumes untouched tasks. No human needs to issue
those commands between a successful bounded repair and a proved continuation.

The parent archives executing source bytes before launch. Later allowed source
changes can create another documented epoch when all actions and charges are
settled. Existing executions and grades are copied exactly; they are not rerun.
Receipt expiry triggers new actual zero-call qualification on a parent retry.
Unknown action/grade intents or charges, missing proofs, a true argument mismatch,
forbidden source/configuration changes, exhausted retries or an unsupported
reconstruction require concrete escalation. Automatic repair does not mean
repeating a possibly completed mutation or rerolling a failed control.
